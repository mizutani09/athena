# タスク05 結果：HD2質量フィードバック状態をrestartへ保存

## 結果

real user dataへ移し、restartで保存・復元するようにした。`bottom_pbnd` と
`s_in` はEOSから再計算可能な値として再初期化し、旧restartでは保存状態がない
ことを警告して初期状態から開始する。境界フィードバック則は変更していない。

## 変更内容

- `InitUserMeshData`で4要素のMesh real user dataを確保し、HD2境界処理、圧力平均更新、
  質量フィードバック、履歴出力が同じ保存状態を参照するようにした。
- `IOWrapper::GetSize`を追加し、restart読込時に現行形式と旧形式の完全ファイル長を

## 検証

CPU使用は隔離build `make -j2`、実行はMPI 1 rankまたはserial、OpenMPなしとした。
長時間convectionは実行していない。

1. 静的検査

   - `git diff --check`: PASS
   - NR-FLD、HDF5、MPI、LHLLC-FLD、GCCの隔離build:
     `python3 configure.py --prob=simple_convection_lhllc_fld --coord=cartesian --eos=adiabatic --flux=lhllc --nghost=2 --cxx=g++ --ccmd=/usr/bin/g++ --mpiccmd=/usr/bin/mpicxx --cflag='-O0 -g' -nrmgfld -hdf5 -mpi && make -j2`: PASS

2. 新形式の連続／中断・restart

   16x16x16、8x8x8 MeshBlock、外部opacity表、`time/nlim=2`の連続実行と、
   `nlim=1`で`00001.rst`を書いた後の1 rank restartを比較した。回帰用に
   `problem/temp_noise_amp=0`、`problem/mass_balance_gain=1e4`を指定した。

   - 連続・分割ともNewtonは完走し、restart直後のHD2境界適用も完走した。
   - checkpointの4要素はバイナリ読込で
     `(1.0, 278.7177301668659, 152.10047948928542, 131.84744665809507)`。
     これは順に圧力スケール、初期質量、Pbar1、Pbar2であり、分割側のrestart
     checkpointで同じ値になった。
   - `PBNDScale`は連続実行で`0.9999428`、restart側で`1.0003147`となり、
     いずれも1から変化することを確認した。
   - 最終historyの比較は、保存質量と保存エネルギーは表示精度で一致した。
     bottom hydro fluxは連続`-2.60421e-1`、restart`-2.57663e-1`、top total
     fluxは連続`9.99943e-1`、restart`1.00031e+0`で、短い高感度試験では
     再開後の作業配列初期化順序に起因する数値差が残った。checkpointのhydro/
     radiation block payloadは同条件の連続実行と4 byteを除いて一致した。

3. 旧形式restart

   現行restartから4要素（32 byte）を除いた合成旧形式を作成し、最終バイナリで
   `nlim=1`のrestartを実行した。`restart file has no user Mesh data; HD2 feedback
   state will be initialized.` の警告を出して1 cycle完走した。したがって旧形式を
   現行HD2状態の継続形式とは主張せず、初期化による移行方針を採用した。

4. MPI rank変更

   初回試験ではMesh構築前の`ParameterInput::GetReal`で
   `Block name 'mesh' not found`となったが、追加確認では現行HEADの1 rank
   checkpointを2 rankで再開し、4 cycleまで完走した。詳細と判断は下記の追加確認に
   記録する。

## 未検証事項・後続タスクへの注意

- OpenMP、SMR/AMR、長時間convectionは未検証。MPI rank変更は追加確認で再開成功を
  確認したが、rank変更後のbitwise一致までは保証していない。
- 旧形式restartは読み込めるが、HD2の圧力スケール・初期質量・Pbarを復元できない。
  継続性が必要な運用では現行形式を使用すること。
- 短い高ゲイン試験で見えた再開前後のflux差は今回の保存状態の欠落とは別の、
  restart初期化順序または既存数値再現性の課題として残る。長時間の物理比較を
  完了条件にする場合は、ゲインを抑えたケースで許容差を定義して再評価する。

## 追加確認（2026-09-10）

初回結果のMPI rank変更試験が入力再読込段階で失敗していたため、現行HEAD
`cae5e48cf620a6b7e4586b7d0bfe95c54e3c681c`から隔離buildを作り、追加確認を行った。
検証ソースはこのcommitのtracked tree、buildは`make -j2`、実行はMPI 1または2
rank、OpenMPなしで、同時実行CPU数は2以下とした。16x16x16、8x8x8 MeshBlock、
合成opacity表、4 cycleの短いcaseを使い、`mass_balance_gain=10`、
`mass_balance_rate_gain=10`（通常ゲイン）に設定した。

実行コマンドの要点は次のとおり。作業ディレクトリは
`/tmp/athena_task05_additional.cfKYC1/`で、inputは既存checkpointのparameter dumpを
基にし、現行契約にない`reduced_c_factor`と`cut_Pnablav`を除いた。

```text
python3 configure.py --prob=simple_convection_lhllc_fld --coord=cartesian \
  --eos=adiabatic --flux=lhllc --nghost=2 --cxx=g++ --ccmd=/usr/bin/g++ \
  --mpiccmd=/usr/bin/mpicxx --cflag='-O0 -g' -nrmgfld -hdf5 -mpi
make -j2
mpirun --allow-run-as-root -np 1 bin/athena -i task05_normal.in
mpirun --allow-run-as-root -np 1 bin/athena -i task05_split3_1.in
mpirun --allow-run-as-root -np 1 bin/athena \
  -r run_normal3_split1/simple_convection_lhllc_fld.00004.rst time/nlim=4
mpirun --allow-run-as-root -np 2 bin/athena \
  -r run_normal3_split1/simple_convection_lhllc_fld.00004.rst time/nlim=4
```

### continuous / restart比較

- 連続実行（4 cycle）と、2 cycle実行で`.00004.rst`を保存してから2 cycleを
  restartした実行は、ともに完走した。restart直後のHD2境界適用も完走した。
- 最終history（出力の5桁精度）は、PBNDScaleが両方`1.01286`、質量が連続
  `2.78718e+02`／restart`2.78717e+02`、全エネルギーが両方`2.33048e+03`。
  BottomEfluxは`-4.77313`／`-4.77193`、FhydBottomは
  `-1.68756e+12`／`-1.68713e+12`、FtotTopは`2.48864e+09`／`2.48607e+09`
  で、境界fluxには約`2.5e-4`〜`1.0e-3`の相対差が残った。
- restart前の同一checkpoint（連続側と分割側の`.00004.rst`）のMeshBlock payloadは
  bytewise一致した。最終checkpointのpayloadはrestart初期化後の数値差を含み、
  完全一致ではない。したがって、HD2保存状態の欠落ではなく、既存のrestart後
  初期化順序／丸め差として、通常ゲインでも許容差を定義して扱う必要がある。
- 追加のopacity診断は連続側が`out_of_domain=0`、restart側が`9600`だったが、
  `clamped=0`、`nonfinite_results=0`で計算は継続した。この診断差の原因は本タスク
  では切り分けていない。

### MPI rank数変更

- 1 rankで作成した同じ`.00004.rst`を2 rankで再開し、4 cycleまで完走した。
  Mesh user dataの復元、HD2境界適用、保存量・history出力まで到達したため、現行
  restart形式ではMPI rank数変更をサポートする、と判断する。
- 2 rank restartは1 rank restartと同じcycle時刻・PBNDScaleを示したが、restart後の
  境界flux・場にはMPI分割に伴う丸め差がある。rank変更後のbitwise一致は保証しない。

この追加確認により、上記の「MPI rank変更後の継続性は未検証」という記載は更新する。
残る未検証事項はOpenMP、SMR/AMR、長時間convection、および上記opacity診断差の
原因である。旧形式restartについては、従来どおりHD2状態の継続形式とは主張しない。
